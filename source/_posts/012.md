## 我用 Claude Code 半天做了一个全栈 AI 股票分析面板

 **TL;DR**：从零开始，**Next.js 16 + DeepSeek + Supabase + Render**，行情拉取 → LLM 结构化分析 → 数据库落库 → 线上部署，全流程半天完工。
 
 线上 Demo：<https://stock-ai-r7qr.onrender.com>
 
 源码：<https://github.com/xwwcyber/stock-ai>

> 这篇不是讲项目本身，而是复盘**我是怎么和 Claude Code 配合的**——哪些事让 AI 主导更快、哪些事必须自己亲自定夺，以及一套我后续会反复用的「AI 协作工作流」。

---

## 为什么写这篇

很多人聊 AI 编码工具都停在「我让它生成了一段代码，省了 10 分钟」。但真正能体现 AI 价值的，是在一个**真实的、多技术栈的、有部署链路的**项目里，把 AI 当成一个不会累、不会烦、能记住上下文的搭档来用。

这个 stock-ai 项目刚好覆盖了一个全栈 AI 应用的所有关键环节：

- 第三方数据接口接入（东方财富）
- LLM 调用与结构化输出（DeepSeek）
- 数据库 schema 设计与 RLS（Supabase Postgres）
- 前端交互（Next.js App Router + Tailwind）
- 部署与环境变量管理（Render）

每一环我都和 Claude Code 配合过，有些环节几乎完全交给它，有些环节我必须出手。复盘下来，我总结出 5 个阶段的协作模式，下面挨个讲。

## 阶段 1：需求拆解 / 技术选型

**我做的事：**给出业务目标——「输入股票代码，调用免费 API 拿行情，LLM 给一段结构化分析，存到数据库，部署上线」。

**让 AI 做的事：**

- 列举可选的免费行情数据源（东方财富 / 新浪财经 / Yahoo Finance），各自优劣
- 列举可选的 LLM 服务商（OpenAI / DeepSeek / 通义 / Moonshot），按价格、国内可达性、JSON mode 支持度排序
- 给出 Supabase vs Neon vs Vercel Postgres 的对比
- 用一段话总结**最小可行架构**

> **协作要点：技术选型不是让 AI 替你选，而是让 AI 把候选方案压缩成一张对比表，你拿着表做决策。**

最后我选的组合：
- 行情：东方财富（零 API Key，A股/港股/美股全覆盖）
- LLM：DeepSeek（兼容 OpenAI SDK，便宜，国内稳定）
- 数据库：Supabase（免费 500MB + REST API + RLS）
- 部署：Render Free Tier（GitHub 直连）

这一步耗时约 20 分钟，全程对话式。如果让我自己 Google 比较，至少要 1-2 小时。

## 阶段 2：脚手架与样板代码

这一步基本完全交给 AI。我的提示词只有一句话级别：

> "用 Next.js 16 App Router + TypeScript + Tailwind 4 初始化项目，给我一个最简版本，有 `app/page.tsx`、`app/api/quote/route.ts`、`lib/eastmoney.ts` 三个文件即可，先用 mock 数据跑通。"

Claude Code 在自己的环境里把项目跑起来了，生成的代码包含：

- `lib/eastmoney.ts` 里的多市场代码识别（A股 6 位、港股 5 位、美股字母）
- API Route 的标准请求/响应处理
- 前端的 loading / error 状态

我做的事只有：

1. **Code review**：检查 TypeScript 类型、错误处理是否完整
2. **拆掉过度设计**：AI 一开始加了一个 `useReducer` 管状态，我让它换成普通 `useState`——三个状态不需要 reducer
3. **指出 Next.js 16 的破坏性变化**：项目里有个 `AGENTS.md` 提示「This is NOT the Next.js you know」，我让 AI 先查 `node_modules/next/dist/docs/`，避免它套用旧版 API

> **协作要点：让 AI 写样板代码的同时，必须 review。AI 的默认习惯是「全部都写」，你要主动砍掉不需要的东西。三行重复代码优于过早抽象——这条规则你不说，AI 不会知道。**

## 阶段 3：Prompt 设计与 LLM 集成（重头戏）

这是整个项目**唯一让我反复打磨**的环节，也是最体现 LLM 应用工程能力的部分。

### 问题：LLM 默认非常喜欢「乱说话」

要 LLM 输出 JSON，初版 Prompt 写「请输出 JSON 格式的分析结果」，模型会：

- 在 JSON 前后写一堆解释（"以下是分析结果：..."）
- 用 ` ```json ... ``` ` markdown 代码块包裹
- 字段名拼写不一致（`risk_level` vs `riskLevel`）
- 枚举值擅自翻译（`高/中/低` 代替 `High/Medium/Low`）

任何一种都会让前端 `JSON.parse` 炸掉。这不是 LLM 的 bug，是它的**默认行为**——它被训练得「友好」「会解释」，而不是「机械精确」。

### 解法：三层防御

我和 Claude Code 来回迭代了 5 轮，最终定稿的是**三层防御**结构：

#### 第一层：System Prompt 写死格式契约

```ts
const SYSTEM_PROMPT = `你是一名资深股票分析师。基于用户给出的实时行情快照，输出客观的短评。

返回必须是严格的 JSON 对象，字段如下：
- summary: string（中文，120-200 字，总结当前价格表现、成交活跃度、相对昨收的位置，避免任何投资建议）
- sentiment: "Bullish" | "Neutral" | "Bearish"（基于技术面信号判断当下情绪）
- risk_level: "Low" | "Medium" | "High"（结合波幅、换手率、估值给出风险）
- key_factors: string[]（3-5 条最关键的支撑/风险点，每条不超过 30 字）

只返回 JSON，不要任何解释性前后缀，不要使用 markdown 代码块包裹。`;
```

**关键技巧**：

| 技巧 | 为什么有效 |
|---|---|
| 逐字段列约束（类型 + 取值 + 字数限制） | 远比一句「输出 JSON」具体，模型可遵循的颗粒度细 |
| 枚举值用 TypeScript 字面量写出 | 模型会照抄 `"Bullish" \| "Neutral" \| "Bearish"`，不会自创 `Up/Down` |
| 显式禁止 markdown 包裹 | 阻止 ` ```json ... ``` ` 这种破坏 JSON.parse 的格式 |
| 加「避免任何投资建议」 | 合规友好，同时降低模型发散 |

#### 第二层：API 调用层强制 JSON 模式

```ts
const completion = await client.chat.completions.create({
  model: 'deepseek-chat',
  messages: [
    { role: 'system', content: SYSTEM_PROMPT },
    { role: 'user', content: buildUserPrompt(quote) },
  ],
  response_format: { type: 'json_object' },   // ← 解码层强制
  temperature: 0.4,                            // ← 降低发散度
  max_tokens: 800,
});
```

`response_format: { type: 'json_object' }` 是 OpenAI 兼容协议的 **解码层约束**，从根本上杜绝非 JSON 输出——哪怕模型「想」加前缀也输不出来。

`temperature: 0.4` 不是越低越好。股票分析需要轻微发散，但又不能天马行空——0.4 是我试了 `0.0 / 0.2 / 0.4 / 0.7` 之后的平衡点。

#### 第三层：后端运行时校验

```ts
function validate(data: unknown): Analysis {
  if (!data || typeof data !== 'object') throw new Error('LLM 输出格式错误');
  const obj = data as Record<string, unknown>;

  const summary = typeof obj.summary === 'string' ? obj.summary : '';
  const sentiment = obj.sentiment;
  const risk_level = obj.risk_level ?? obj.riskLevel;          // 兼容 camelCase
  const key_factors = Array.isArray(obj.key_factors)
    ? obj.key_factors.map(String).slice(0, 6)
    : Array.isArray(obj.keyFactors)
      ? (obj.keyFactors as unknown[]).map(String).slice(0, 6)
      : [];

  if (!summary) throw new Error('summary 字段缺失');
  if (sentiment !== 'Bullish' && sentiment !== 'Neutral' && sentiment !== 'Bearish') {
    throw new Error(`sentiment 取值非法: ${String(sentiment)}`);
  }
  if (risk_level !== 'Low' && risk_level !== 'Medium' && risk_level !== 'High') {
    throw new Error(`risk_level 取值非法: ${String(risk_level)}`);
  }

  return { summary, sentiment, risk_level, key_factors };
}
```

即使前两层都失守，这里也拦得住「字段缺失 / 枚举乱写 / 类型错误」。兼容 `riskLevel` / `risk_level` 两种命名，但**不接受** `Up/Down`、`高/中/低` 这种擅自翻译。

> **协作要点：Prompt 工程不是「让 AI 帮你写 Prompt」就完事。AI 第一版 Prompt 通常太「礼貌」，缺少强约束。你要做的是反复对抗测试——拿真实数据跑 20 次，看输出有没有任何一次破坏 JSON，破坏了就加一条约束，直到 100 次都不破坏为止。**

## 阶段 4：Debug（最体现 AI 价值的环节）

这一节我要详写，因为它是我整个项目里**对 AI 协作收益感受最深的一段**。

### 现象

集成 Supabase 完成第一次本地联调，请求 `/api/analyze` 返回看起来正常：

```json
{ "quote": { ... }, "analysis": { ... }, "saved": false, "record_id": null }
```

但 `saved: false`。看 dev server 日志：

```
[save] 落库失败: Error: Supabase 写入失败: Invalid path specified in request URL
```

PostgREST 错误码 `PGRST125`，错误文案 5 个英文单词，没有堆栈细节。

### 传统排查 vs AI 协作排查

**传统做法**：Google「PGRST125 Supabase」→ 翻几篇英文 Issue → 猜几个原因 → 改代码试。预计 30-60 分钟。

**AI 协作做法**：

把这条错误直接丢给 Claude，并附上 `lib/supabase.ts` 的源码。Claude 立刻给出 4 个候选原因：

1. ⚠️ `SUPABASE_URL` 末尾带了 `/` 或多余路径
2. 表不在 `public` schema
3. Data API 没启用（项目创建时的安全选项）
4. 客户端版本与 Publishable Key 不兼容

**关键的一步**：Claude 主动说「我不能直接读你的 `.env.local`（凭据有泄露风险），但我可以帮你写一个**脱敏诊断脚本**」。

```js
// 关键脱敏打印：只显示前后几位
console.log('URL :', url);
console.log('KEY :', key.slice(0, 12) + '...' + key.slice(-6),
            `(共 ${key.length} 字符)`);

// URL 格式校验
if (url.endsWith('/')) console.warn('⚠️  URL 末尾不应有 /');
if (!/^https:\/\/[a-z0-9]+\.supabase\.co$/.test(url)) {
  console.warn('⚠️  URL 格式可能异常');
}

// 逐层诊断：根路径 → 读表 → 写表
const root  = await fetch(`${url}/rest/v1/`, { headers: { apikey: key, ... } });
const read  = await fetch(`${url}/rest/v1/analyses?select=*&limit=1`, ...);
const write = await fetch(`${url}/rest/v1/analyses`, { method: 'POST', ... });
```

跑一次，问题立刻浮现：

```
URL : https://rvjgpyxorigsjxzkrbhu.supabase.co/rest/v1/    ← 问题暴露！
⚠️  URL 末尾不应有 /
⚠️  URL 格式可能异常，标准形如 https://abc123.supabase.co
```

### 根因

`SUPABASE_URL` 末尾**多了 `/rest/v1/`**——我从 Supabase Dashboard 的 **API Docs** 页面复制了完整 endpoint，而不是从 **Project URL** 字段拿。

`@supabase/supabase-js` 内部会自己拼 `/rest/v1/<table>` 路径，所以最终请求 URL 变成：

```
https://xxx.supabase.co/rest/v1/  +  /rest/v1/analyses
= https://xxx.supabase.co/rest/v1/rest/v1/analyses       ← 路径根本不存在
```

PostgREST 找不到路径，返回 `PGRST125 Invalid path specified in request URL`——错误信息其实是**精准的**，只是没堆栈让人不知道从哪查。

### 修复

`.env.local` 改一行：

```diff
- SUPABASE_URL=https://rvjgpyxorigsjxzkrbhu.supabase.co/rest/v1/
+ SUPABASE_URL=https://rvjgpyxorigsjxzkrbhu.supabase.co
```

实际耗时：从看到错误到 fix 完成，约 8 分钟。

### 这个 Debug 故事的几条心得

| 心得 | 说明 |
|---|---|
| **配置类错误用诊断脚本，而不是改源码** | 写一段独立的连通性测试，比反复改 SDK 调用更快定位 |
| **脱敏打印是 AI 协作的必要技巧** | 让 AI 看真实凭据是错的，但「URL 长这样、Key 长 46 字符、前缀是 sb_publishable_」这种结构信息可以放心给 |
| **错误码搜文档，别搜文案** | `PGRST125` 比「Invalid path specified」精准 10 倍——错误码是稳定的，文案会随版本变 |
| **诊断脚本留在仓库里** | 我把 `scripts/check-supabase.mjs` 提交了，以后换环境直接 `node --env-file=.env.local scripts/check-supabase.mjs` 就能复测 |

## 复盘：5 条可复用的 AI 协作心得

写完这个项目，下面 5 条是我会持续用下去的：

### 1. 让 AI 当「候选方案压缩器」，而不是「决策者」

技术选型、库对比、架构方案——让 AI 列出 3-5 个候选，每个标注优劣，你来拍板。**永远不要让 AI 替你做架构决策**，因为它不知道你的实际约束（团队偏好、运维能力、成本承受度）。

### 2. 样板代码全权委托，但 Code Review 不能省

AI 生成的代码 90% 能用，但有 10% 是「过度设计」「不必要的抽象」「错误的库版本假设」。Review 时重点看：

- 有没有引入用不到的依赖
- 有没有把简单逻辑写复杂
- 有没有套用过时的 API（特别是 Next.js 这种快速演进的框架）

### 3. Prompt 工程是反复对抗测试，不是一次写好

第一版 Prompt 一定不够强约束。**用真实数据跑 N 次，看到一次破坏就加一条约束**，直到 0 破坏。三层防御（System Prompt + API 参数 + 后端校验）任何一层都不能省。

### 4. 配置类错误优先用诊断脚本

环境变量、API Key、URL 格式这类问题，**不要在主代码里加 console.log 反复重启**——让 AI 帮你写一个独立的诊断脚本，跑一次就能定位。脱敏打印是关键技巧。

### 5. 把 AI 当成「不会累的搭档」，而不是「魔法工具」

AI 不会一句话变出整个项目。你要做的是：

- 把任务拆成 5-20 分钟一段的小问题
- 每一段都给清楚的上下文（目标 + 现状 + 约束）
- 拿到结果立刻验证，错了立刻反馈
- 节奏快、迭代多、信任但 review

这种节奏下，半天能做的事比你想象的多得多。
